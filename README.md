# CTU OmniTrain

An AutoML platform for training, evaluating, and exporting models (Ludwig, scikit-learn for quick tabular and text
baselines, and Ultralytics YOLO for
image classification and object detection) without writing config by hand. A user creates a **project** bound to one of a fixed set of **tasks** (e.g. image
classification, text classification, tabular regression); each task is pinned to one of four
**modalities** (vision / text / audio / tabular). From there the flow is: upload data into the
project's dataset pool → label it → cut an immutable **snapshot** → train a **run** with a trainer backend →
watch live metrics → run **inference** → **export** the result as a raw model, a devkit,
or a deployable app.

## Architecture

```
                    ┌─────────────┐
                    │ YARP (proxy)│  catch-all → web, /api/** → api
                    └──────┬──────┘
               ┌───────────┴────────────┐
               ▼                        ▼
       ┌───────────────┐        ┌─────────────────────┐
       │  web (Vite)    │       │ api (Python)         │
       │  React 19      │ axios │ FastAPI + SQLAlchemy │──▶ Postgres 18
       │  TanStack      │──────▶│ job queue + Ludwig   │
       │  Router+Query  │ Orval │ (train/export/infer) │──▶ RustFS (S3-compatible)
       │  Mantine+Tailwind      └─────────────────────┘
       └───────────────┘
```

Everything is orchestrated by a **.NET Aspire** AppHost written in TypeScript
(`apphost.mts`, no C# anywhere in this repo). Aspire wires up Postgres, an S3-compatible object
store (RustFS), the Python `api` service, the Vite dev server, and a YARP reverse proxy that
fronts everything on one origin (avoids CORS, lets the SPA and API share cookies).

| Component | Path | Stack |
|---|---|---|
| AppHost | `apphost.mts` | Aspire TypeScript AppHost |
| Backend | `server/` | Python + FastAPI + SQLAlchemy (async) + Alembic + Ludwig + boto3 |
| Frontend | `web/` | React 19 + Vite + TanStack Router/Query + Mantine + Tailwind v4; API client generated by Orval |
| API contract | `schema/openapi.json`, `schema/task_registry.json` | generated from the backend, committed, drift-checked in CI |

### One service, not two

The backend used to be a Bun/Elysia gateway plus a Python worker joined by NATS JetStream. The
only reason for the split was that Ludwig is Python-only, and the horizontal scalability NATS
bought was never used (one replica of each). They are now a single FastAPI process: dispatching
a job is a function call, run events are rows in Postgres, and the API's request/response models
are the only schema.

**It must run as exactly one process** (`workers=1`, asserted at startup). The in-process event
bus, the API-key rate limiter, the loaded-model cache and the GPU all assume it, and forking after
a CUDA context exists is not survivable. Never run it with `--reload`, gunicorn or multiple workers.
That one process is still the only thing that writes run state: training can also happen on other
machines (see "Remote training workers"), but they report back to it over HTTP.

**Jobs.** The domain tables are the queue: `training_runs`, `model_exports` and `custom_models` carry `attempt`,
`max_attempts`, `available_at`, `claimed_by`, `lease_expires_at` and `last_error`. A dispatcher
claims work with `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED)` and runs it on a lane
with its own executor: `train` (one at a time), `export` (two) and `validate` (one, for bring-your-own
model checks). The house rule is that **the
status column is the lock**: every transition is a guarded compare-and-swap
(`UPDATE ... WHERE status = ... RETURNING`), and zero rows means someone else got there first.
Training is never retried; export is (3 attempts, 30 s apart); validation retries only an unexpected
error such as a network failure (3 attempts), never a model that is simply not acceptable.

**Remote training workers.** A run can train on another machine instead of this server's GPU, with no
change to any trainer backend. A worker is a second process, `python -m omnitrain.worker`
(`server/omnitrain/worker/`, image recipe in `server/Dockerfile.worker`), that you start on any GPU box:
a rented VM, a lab machine. It **pulls**: it asks `POST /api/worker/claim` for a queued run every few
seconds, trains it with the same `jobs/run_core.execute` the server's own `train` lane uses, and reports
back through `/api/worker/runs/{id}/events` (metrics, heartbeat; the answer says whether the run was
canceled) and `/complete` (outcome and evaluation). It never opens a database connection and the API
never sends it storage secrets: it reads the snapshot and writes the results to S3 directly, with its own
`S3_ENDPOINT` / `S3_ACCESS_KEY` / `S3_SECRET_KEY`. Those must reach the same buckets the server uses,
because snapshot parquets embed absolute `s3://theseus-datasets/...` URIs; for a local RustFS that
means exposing its port to the worker (a tunnel or VPN).

Register a worker under Admin > Workers: it gets a `thwk_...` bearer token (hashed like an API key, shown
once). Nobody chooses where a run trains. A new run is held back for up to
`REMOTE_CLAIM_GRACE_SECONDS` (20) while an enabled worker that is online (heard from within
`WORKER_ONLINE_SECONDS`, 30), idle, and able to train the run's backend exists; if no worker takes it in
that time, the server trains it itself. A worker holds one run at a time.

A run on a bring-your-own model goes to a worker only when the worker can get the model **by itself, with no
secret**, and the backend has opted in (`TrainerBackend.remote_custom_models`, today `video`, `pytorch` and `llm`: a fine-tuned
Hugging Face video, image or language model is saved as a self-contained folder, so it never needs the base model's files again).
The run spec then carries a `customModel` description; the worker fetches the files with the server's own code
(`custom_models.ensure_local`: an uploaded bundle from S3 with its checksum re-checked, or a public Hub model at
its pinned revision, fetched anonymously whatever token the machine has; each `ModelSource` in `omnitrain/plugins/model_sources/` declares which
of its models qualify) into its own temp dir and swaps the
server's path for that one in the config. Everything else trains on the server: a private or gated Hub model
(it needs its owner's saved token, which never leaves the server), and every Ludwig custom model (its checkpoint
re-reads the model from the path in its config, which would be the worker's). The two sides
must agree on `schemas/worker.PROTOCOL_VERSION`, which is bumped when the wire contract, a run's S3
layout or what a backend must do changes, and should be built from the same commit.

A server restart does not touch a remote run (it fails only runs it was training itself); a worker that
dies is caught by the heartbeat reaper like a hung local thread; revoking a worker fails its run at once.
Cancel reaches a worker through its next progress call, so it stops at an epoch boundary as local runs do.

**Inference is not a job.** A prediction runs inside the request that asked for it and its result is
the response (`services/inference.py`): nothing is queued, stored or polled. At most
`INFERENCE_CONCURRENCY` run at once; a request that cannot get a slot is answered `503` with
`Retry-After`, and one that exceeds `INFERENCE_TIMEOUT_SECONDS` is a `504`. A restart mid-request
drops that request (the client retries). Batch scoring works the same way: the CSV goes in, the
scored CSV comes back.

**Restarts.** On startup, before the dispatcher runs, a recovery pass fails any `running` training
run ("Server restarted during training") and re-queues `running` exports and `validating` custom
models. A restart therefore ends in-flight training. A reaper loop also fails a training run whose
heartbeat stops (a hung thread) and reclaims expired export and validation leases.

**Run events and live updates.** Metrics and status changes are appended to `run_events`
by a single writer task (a `BIGSERIAL` is not commit-ordered, so concurrent writers would let a
reconnecting client skip events). The same transaction updates the projection
(`training_runs.status`, `training_metrics`, `run_evaluations`). `GET /api/runs/{id}/events`
streams them over SSE with `Last-Event-ID` replay: subscribe, then read the backlog, then go live.
Training output is not captured: runs have no log stream, log file or Logs tab.

**Cancel.** `training_runs.cancel_requested_at` is the durable record; an in-process
`threading.Event` is what the training thread polls each epoch. A run stops via `TrainingAborted`,
never `KeyboardInterrupt`, which uvicorn would treat as a shutdown signal.

**Auth.** Stateless JWT access tokens (15 min, HttpOnly cookie, verified with no database read)
plus an opaque, hashed, rotating refresh token (30 days, `Path=/api/auth`) so logout and reuse
detection work. Passwords are argon2id. Cookie auth is protected against CSRF by `SameSite=Lax`
plus an `Origin` check on unsafe methods. Third-party callers use API keys (`thsk_...`, hashed,
rate limited) on `/api/v1/**`, which is exempt from the cookie checks.

**Database migrations** (Alembic) run in `main.py` before uvicorn starts, not in the FastAPI
lifespan, so a slow migration cannot fail the health check.

### Task registry

Tasks are plugins: each is one `Task` subclass in `server/omnitrain/tasks/builtin/` (a module dropped
there registers on the next backend restart), and `server/omnitrain/domain/task_registry.py` is the
lookup over them and the single source of truth every other piece derives from. A task declares, per task, which modality it belongs to, what shape a dataset item takes
(`itemSpec.payload`: `file` / `inline_text` / `record`), what annotation type it needs, the snapshot
columns, and the inference input/output kinds. It says nothing about how a task is *trained*: that is a
trainer backend's job (`server/omnitrain/plugins/backends/`, one package per framework). The frontend's task
picker, the per-modality upload/labeling UI and snapshot column derivation are all driven off this one
descriptor per task, so adding a new task's data side means adding one class, not touching five files:
`projects.task` is free text, so there is no enum or migration, and `POST /api/projects` rejects an id
no installed task defines. The picker's icon and blurb come from `web/lib/task-meta.ts` (generic fallback). The frontend reads it from the generated `schema/task_registry.json` (`web/lib/tasks.ts`), with
the inference input/output kinds already evaluated.

#### Object detection data

`object_detection` stores **one `annotations` row per box** (`annotation_type = 'bounding_box'`, with a
`class_id`). `label_structured` is `{x, y, w, h}`: the top-left corner and the size, each a fraction
(0..1) of the whole image as displayed. Fractions rather than pixels, so a box survives a thumbnail or a
re-upload and nothing at training time needs the image's size. An image with nothing in it carries a
single marker row (`bounding_box`, no class, `{"background": true}`): a detector must learn what *not* to
fire on, and that is different from an image nobody has labelled yet, which a trainer leaves out. The
rules live in `server/omnitrain/domain/boxes.py`; the snapshot's `boxes` column is a JSON list of
`{label, x, y, w, h}` per image (`null` while unlabelled). A class belongs to one box, so the bulk "assign
class" action does not apply; boxes are drawn on the image in the item drawer, or imported with their
labels from a YOLO-format archive (Upload → Import YOLO dataset).

### S3 key layout

Three buckets (`server/omnitrain/services/storage.py`), content-addressed where it matters. They keep their
pre-rename `theseus-*` names: every snapshot parquet stores absolute `s3://theseus-datasets/...` image URIs, so
renaming a bucket means copying its objects *and* rewriting those files. The same goes for the `_theseus_item_id`
snapshot column, the Docker volumes `ctu-theseus-database` / `ctu-theseus-rustfs` and the Postgres database
`ctu-theseus-db`.

```
theseus-datasets/
  pool/{projectId}/{hash[0:2]}/{hash}{ext}   content-addressed, deduped upload pool
  snapshots/{versionId}/dataset.parquet      immutable, cut from the pool
  snapshots/{versionId}/manifest.json
  snapshots/{versionId}/preprocessed/...     preprocessed replacements built with that snapshot (not pooled)
  snapshots/{versionId}/augmented/...        augmented copies built with that snapshot (not pooled)
  thumbnails/{size}/{original key}.jpg       cached JPEG thumbnails of image items, made on first request

theseus-training/
  {runId}/config.yaml                        the backend's compiled training config
  {runId}/results/                           the backend's own output (Ludwig: its output tree incl.
                                             training_set_metadata.json; YOLO: best.pt, names.json, results.csv)

theseus-models/
  {runId}/model.{onnx|pt2}                   converted export artifacts (shared by formats)
  {runId}/bundles/{exportId}.zip             assembled devkit/app bundles
  {runId}/expected.json                      golden sample for devkit verify scripts
  custom/{modelId}/bundle.zip                a bring-your-own model upload
```

Dataset pool uploads are deduplicated per-project by sha256: the same file uploaded twice
(or referenced from two dataset versions) is stored once.

The **Add data** drawer is one flow for every task: stage (drop files and folders, type or paste text, import a CSV),
review (a summary card over class lanes of previews to spot a misfiled picture by eye, or the folders, or a flat filterable table), upload.
After a drop the browser hashes each file and asks `POST /api/projects/{id}/items/preflight` which contents the draft
already holds, so those are marked "not sent" before any bytes move (advisory: the upload route still dedups on its
own). A split left on *auto-split* is drawn in the browser when Upload is pressed (stratified by class, default
80/10/10, only over the files being added). Pressing Upload hands the batch to a background job, shown in the upload
tray at the corner of the app, so it carries on if the drawer is closed; failed or unsent files stay in the job for a
retry. Jobs live in memory, so a page reload ends one.

### Snapshot preprocessing and augmentation

Both are chosen when a **snapshot** is created, not when training, and preprocessing runs first.

**Preprocessing** ops are deterministic and each is scoped to whichever splits (train/validation/test)
the snapshot builder selects for it. A preprocessed item **replaces** its original in the snapshot's
membership for exactly those splits — nothing is added, unlike augmentation below. An item whose ops
leave it unchanged, or whose split none of them selected, stays the pool item it already is. A
`fit`-needing op (e.g. tabular standardize) always fits on the train split's samples, even when train
isn't one of its own selected splits, so nothing about validation or test leaks into how a value is
scaled. Shipped ops: image (resize, grayscale), text (lowercase, normalize whitespace), audio
(resample, mono) and tabular (standardize, min-max).

**Augmentation** can add N randomly perturbed copies of every item in the **train** split (validation
and test stay real, so metrics measure real data), made from whatever is in the train split after
preprocessing ran — so a copy carries forward any preprocessing its source item had. Shipped ops: image
(flip, rotate, brightness, contrast, saturation, blur, crop, noise), text (word deletion, swap,
duplication, typos), audio (gain, noise, time shift, speed) and tabular (noise, scale jitter, feature
dropout).

During the build, both are materialized as real `dataset_items` rows — `source_item_id` always points
at the pool ancestor directly, even for an augmented copy made from a preprocessed item (there is never
a chain of derived items) — with the modality features and a copy of the original's labels, so the
parquet, manifest, split counts and the Snapshots page all include them unchanged. The Snapshots page
shows "Preprocessed"/"Augmented" badges and an Original / Augmented filter, and the training form has
neither option: both are fixed once the snapshot is built.

Preprocessed and augmented items are *not* pool items: their files live under
`snapshots/{versionId}/preprocessed/` and `snapshots/{versionId}/augmented/`, pool dedup only considers
originals (`source_item_id IS NULL`), and deleting the snapshot deletes them
(`services/derived_items.delete_derived_items`). Augmented copies are seeded from (snapshot, item, copy
index), so a rebuild reproduces them.

**Adding a preprocessing op:** create a module in `server/omnitrain/plugins/preprocessing/ops/` with a
subclass of `Preprocessing` that sets `id`, `label`, `modality`, a pydantic `Params` model and
implements `apply(sample, params, state)` (no rng: it must be deterministic). **Adding an
augmentation:** the same shape in `server/omnitrain/plugins/augmentation/ops/`, subclassing `Augmentation`
and implementing `apply(sample, params, rng, state)`. Either way, restart the backend:
`GET /api/projects/{id}/preprocessing` or `/augmentations` returns it for projects whose task it
supports (by default label-preserving classification and regression tasks of its modality) and the
snapshot dialog renders its parameters, with no frontend change.

### Export formats

"Download the ONNX file," "give me code I can drop into my own project," and "give me something end
users can just open" are different products with different constraints, so each is its own **export
format**: one Python class in `server/omnitrain/plugins/export/formats/`. The web app has a single
"Export format" combobox filled from `GET /api/export-formats`.

| Group | Formats (ids) | Contents |
|---|---|---|
| Model | `onnx`, `torch_export` | artifact + `preprocessing.json` + `labels.txt` + README (a format is offered only if the run's backend produces its artifact: YOLO produces `onnx`) |
| Model | `hf_model` | a language model's Hugging Face folder (`model/`) + `preprocessing.json` + a Python client, example and verify script; only for a run trained by the `llm` backend |
| Devkit | `python_devkit`, `typescript_devkit`, `csharp_devkit`, `java_devkit` | ONNX model + a generated inference client (source only) + example + a `verify` script where supported |
| App | `pwa_app`, `flutter_app` | a runnable client app (Progressive Web App or Flutter) doing inference on-device/in-browser |

Devkits and apps are ONNX-only: `torch_export` needs PyTorch at runtime, which would make a portable
client a lie. They also implement classification and regression only: a detector's output is a pile of
candidate boxes that needs non-maximum suppression and an undone letterbox, so for object detection only
the plain `onnx` model is offered (the `preprocessing.json` documents the input and output layout for a
hand-written client). Apps are never a server: both run inference entirely on the end user's own device.
Devkits ship **source only**, deliberately with no project/build
file (no `.csproj`, no Gradle, no `package.json`); the bundle's README documents the exact
dependencies to add to your own project instead, since a devkit's job is to hand you working
reference code to integrate, not a standalone scaffold. The apps are the exception:
`pubspec.yaml` (Flutter) and the PWA's `index.html`/manifest are the app's actual required entry
points, not incidental build tooling, so those do ship.

**Adding a format:** create a module in `omnitrain/plugins/export/formats/` with a subclass of `ExportFormat`
that sets `id`, `label`, `group` and `artifact` (a key of `ARTIFACT_FILENAMES` in `backends/base.py`; the
conversion itself is `TrainerBackend.convert`) and implements `assemble(ctx)`. Restart the backend. The
format shows up in `GET /api/export-formats` and in the web combobox; there is no enum, migration or
frontend change. Override `supports(task)` to hide a format for some tasks and set `notice` for a
caveat the UI shows next to it.

Every devkit/app client re-implements the model's pre/postprocessing from a `preprocessing.json`
built server-side by the backend (`TrainerBackend.preprocessing_manifest`) from a file the run wrote:
Ludwig's `training_set_metadata.json`, YOLO's `names.json`. Critically, the class list comes from
that file (Ludwig's `idx2str`, YOLO's `names`), **never** from the `label_classes` Postgres table, since
Postgres has no knowledge of the index order a run assigned. How an image is resized is part of the same
contract: without an `imageResize` the clients squash it to a square (what Ludwig does), and YOLO
classification asks for `shorter_edge_center_crop`, as Ultralytics does; a client refuses a mode it does not
know rather than guess. A detector's graph returns every candidate box, and a video model's takes sampled clips: every generated client
implements the detector's side (confidence filter, non-maximum suppression, an undone letterbox) and only the Python
devkit implements video (frame sampling), as `client_kind(task)` and the formats' `handles` in `formats/_kits.py` say.
A detector's `expected.json` carries the platform's boxes (`detections`) for the verify scripts to match by overlap; a
format that lacks a kind is offered for that task as the bare model. Every generated bundle ships a
golden sample (`expected.json`) plus a verify path (a script for devkit langs, a built-in
self-check screen/button for the PWA/Flutter apps) so a consumer can confirm the reimplementation
actually matches the platform's own inference output before trusting it.

Export is two-phase (`server/omnitrain/jobs/export.py`, `omnitrain/plugins/export/`): the export lane
converts the model (`pending → converting`), then a guarded `converting → assembling` transition
hands off to bundle assembly, which zips (reproducibly: fixed timestamps, model stored
uncompressed), uploads, and records `ready` or `failed` with a checksum. Both final transitions
are compare-and-swap on status, so a stale result never overwrites a row that startup recovery has
already re-queued. Templates ship as package data under `omnitrain/plugins/export/templates/`.

### Administration

`users.role` is `user` or `admin`. On startup the server makes sure an admin exists
(`services/bootstrap_admin.py`): if the database has none, it creates `OMNITRAIN_ADMIN_EMAIL` (default
`admin@omnitrain.local`) with `OMNITRAIN_ADMIN_PASSWORD`. In development an unset password falls back to
`admin12345` and logs a warning; in production nothing is created without a password. It only acts when no
admin exists at all, so it never resets a password or resurrects a deleted account. Separately, list emails
in `OMNITRAIN_ADMIN_EMAILS` (comma separated) and an account with that email becomes an admin when it
registers or signs in. That only ever **promotes**; removing an email does not demote anyone (do that
from Administration > Users). Every `/api/admin/**` route sits behind `require_admin`, which reads the
role from the database on each request rather than trusting the JWT, so a promotion, demotion or
disable takes effect on the very next request. Disabling an account revokes its refresh tokens and API
keys and blocks sign-in; an access token already issued lives out its 15-minute lifetime. The API
refuses to demote or disable yourself or the last active admin.

Admins can switch trainer backends, base models, export formats, preprocessing and augmentation
ops, and whole tasks on or off, globally or for one task (`plugin_settings`). No row means enabled, so
an install with no overrides behaves as it always did, and a task's own setting beats the "all tasks"
one. The registries stay immutable after startup: the switches are a filter that listings and
validation apply through `services/plugin_settings.is_enabled`, a synchronous lookup in a process-local
snapshot (loaded at startup, replaced after every admin write; sound because the service is one
process). A switch only stops **new** use: existing projects, runs and queued exports keep working
(`find_export_format` and `get_backend` are deliberately not filtered). Admins also see every user's
runs and exports and the state of the job queues (Administration > Jobs).

### Imported models (bring your own)

**Naming.** In the UI a **base model** is the pretrained (or from-scratch) starting point a run is
configured with: either one a backend ships (still `builtin` in the API) or an **imported model**
(`custom_models`, `custom:{uuid}`), which is *shared* (global, added by an admin) or *private* to its
owner. What a run produces is a **fine-tuned model**. Only the labels, the web route (`/imported-models`) and
the web component names changed: API fields, DB columns and the `builtin`/`custom` identifiers did not.

A user can fine-tune a model the platform did not ship: a **Hugging Face Hub** reference (public, or
private/gated through the user's own saved token, see below), or **uploaded weights**. An imported model (`custom_models`) is **global** (no owner: an admin adds it for
everyone) or **private** to its owner, and lists the tasks it is offered for. It is addressed as
`custom:{uuid}` in the hyperparameter the backend names for its model choice (`encoderId` for Ludwig),
so it shares the picker with the built-ins. `services/model_catalog.py` decides who sees what; someone
else's private model is indistinguishable from one that does not exist.

Lifecycle: `pending_upload → uploaded → validating → ready | failed`. A Hub model starts at `uploaded`;
an upload waits for the browser to PUT the file straight to object storage through a presigned URL
(`POST /api/models/{id}/upload-url`, then `/finalize`), so gigabytes never pass through the API. The
`validate` lane (`jobs/validate_model.py`) then pins a Hub model to a commit sha (or hashes an upload),
runs the generic file checks and the backend's own (`TrainerBackend.validate_custom_model`), and marks
it `ready`. A model that is not acceptable fails immediately with a message the user can act on.

What is refused, because the files came from a user or a Hub author (`services/custom_models.py`):
pickle-based weights and any code (`.bin`, `.pt`, `.pkl`, `.py`, ...; use `.safetensors`), symlinks,
paths that climb out of the folder, models that need `trust_remote_code` (`auto_map`), private or gated
Hub repos for a model nobody owns (a shared one), and anything over `MAX_CUSTOM_MODEL_BYTES` (default 5 GiB, the S3 single-PUT limit), before
and after decompression.

**Private and gated Hub models.** In Settings > Integrations a user saves a Hugging Face access token
(`PUT /api/integrations/huggingface`). It is checked with Hugging Face, stored encrypted in
`user_integrations` (Fernet, `services/secrets.py`; the key is `OMNITRAIN_SECRETS_KEY`, else derived from
`JWT_SECRET`) and never returned by the API: only the account name and the token's last four characters are.
It is used only to look up and download models **that same user** imported (`/api/models/inspect`, the
validation job and `ensure_run_custom_model` each resolve the owner's token). A shared (global) model has
no owner, so it is always fetched anonymously and only a public repository passes. With no token the Hub is
asked with `token=False`, so a token configured on the server (`HF_TOKEN`, a cached login) is never used on
anyone's behalf. If the token is later removed, a private model keeps working until its files have to be
fetched again, which then fails with a message asking the user to reconnect.

A trainer backend reads a custom model from a local directory whose path is written into the compiled
config, so the path is deterministic (model id + pinned revision or checksum) and
`services/run_models.ensure_run_custom_model` recreates the files before a run trains, is loaded for
inference, or is converted for export, even after a restart wiped the temp directory. An uploaded
bundle is re-checked against its recorded sha256 when it is put back. A Hub model is re-fetched at
its pinned commit, which needs the Hub to be reachable. `training_runs.custom_model_id` is
`ON DELETE RESTRICT`: deleting a model that any run used **archives** it (hidden, files kept) so those
runs keep loading and exporting.

A backend opts in by implementing `custom_model_kinds(task)`, `validate_custom_model` and the
`custom` argument of `compile`; one that does none of this offers no custom models. Ludwig offers
`hf_transformer` (text classification, through `auto_transformer`), `hf_causal_lm` (the four generative
text tasks, as the `base_model`), `hf_vision` (image classification: any `transformers` vision backbone as
`config.json` + `.safetensors`, through this backend's own `hf_vision` Ludwig encoder in
`backends/ludwig/encoders.py`; a CLIP-style checkpoint with a text tower is refused) and, experimentally,
`timm_image` (image tasks, Hub only, needs the `timm` package installed, and fetches weights by name so it
cannot be pinned). "Any architecture" means any `transformers` architecture: a model that needs its own Python
code is deliberately not supported, because loading it would run the uploader's code on the server.

The `pytorch` backend offers `hf_image` (image classification: a `transformers` classifier or bare backbone of the
ViT, DeiT, BEiT, Swin, Swinv2, ConvNeXt, ConvNeXtV2, ResNet or MobileNetV2 families). The model decides the image size and
normalisation, its weights are loaded strictly (a tensor the files lack is an error, never silently random), and the
trained model is stored as a Hugging Face folder, so it exports through the same six clients as a built-in one and
can train on a remote worker. It also offers `hf_text` (text classification: a BERT, DistilBERT, RoBERTa,
XLM-RoBERTa, ALBERT or ELECTRA encoder, fast tokenizer required), fine-tuned with the model's own tokenizer; the
Python devkit runs that tokenizer (`pip install tokenizers`) and the other five generated clients ship the bare model
plus `tokenizer.json` and a README that says they do not tokenize. `video` offers `hf_video` the same way.

`token_classification` (one tag per whitespace-separated word, `token_tags` annotations, tagged word by word in the item
drawer with the project's classes as the tag set) trains on the `pytorch` backend's `tagger_cnn`, from scratch. Its report counts words and, when the tags
are BIO (`B-PER`, `I-PER`, `O`), whole entities: **Entity F1** is then the run's headline score. The Python devkit tags
text (`predict` returns `[{token, tag, confidence}]`), and so do the TypeScript, C#, Java, PWA and Flutter clients (a
word list the model cannot read past its length gets the `O` tag with no confidence). A Hugging Face encoder (BERT, DistilBERT, RoBERTa, XLM-RoBERTa, ALBERT, ELECTRA) can
be brought as a token classifier (`hf_token`): its own tokenizer reads the words, which it may cut into pieces, and the
first piece of a word carries that word's tag. Only the Python devkit runs it (`pip install tokenizers`); the other five clients
ship the bare model and a README that says they do not implement it.

The four generative text tasks (`text_generation`, `summarization`, `sequence_to_sequence`, `question_answering`) can also
train on the `llm` backend: LoRA adapters (`peft`) on a Hugging Face causal language model that you bring (`hf_causal_lm`;
there are no built-in models). The prompt is the task's input fields under `### name:` headings and the model writes what
follows, graded on the answer's tokens only; when training ends the adapters are merged into the weights and the whole
model is saved as a Hugging Face folder, so a trained run serves from its results alone and can train on a remote worker.
Its report scores generated answers against the written ones (exact match, token F1, ROUGE-1/2/L, loss and perplexity; the
first 200 rows of the evaluated split) and **ROUGE-L** is the run's headline score. A model that does not fit in memory can be
trained on a 4-bit or 8-bit base (QLoRA; needs a CUDA GPU and bitsandbytes), with gradient accumulation and gradient
checkpointing. Its one export is the **Hugging Face model** format: the merged folder with a Python client, example and verify
script (`pip install torch transformers`); a generative model has no fixed-shape ONNX graph, so the generated devkits and apps
do not apply. Ludwig stays the default backend for these tasks (`default_for`).

## Local development

Requires [Bun](https://bun.sh), [uv](https://docs.astral.sh/uv/), Docker, and the
[Aspire CLI](https://aspire.dev) (`aspire`). The `api` container requests an NVIDIA GPU
(`--gpus all`).

```bash
cp .env.example .env       # then set JWT_SECRET; the AppHost refuses to start without it
bun install                # root, web/ and server/ are separate installs
cd web && bun install && cd ..
aspire run                 # equivalent to: bun run dev
```

`.env` is gitignored. `JWT_SECRET` has no default on purpose: a signing key must never live in
version control. Generate it with `openssl rand -base64 32`. Everything else in `.env.example` has
a local-dev default and is only mandatory when `ENVIRONMENT=production`.

This starts Postgres 18, RustFS, the Python `api` service, the Vite dev server and the YARP proxy,
and opens the Aspire dashboard. The proxy serves the whole app on one origin; look at the Aspire
dashboard for the actual URL (see `aspire.config.json`). Postgres 18 is required (`uuidv7()` is a
column default); if you have an older `ctu-theseus-database` volume, delete it. The schema is a
fresh Alembic baseline, not a migration from the old Drizzle one.

### Per-package commands

```bash
cd server && uv run pytest              # needs Postgres 18 (TEST_DATABASE_URI); DB tests skip otherwise
cd server && uv run ruff check . && uv run ruff format --check .
cd web && bun run generate                  # Orval client from schema/openapi.json (output is gitignored)
cd web && bunx tsc --noEmit -p tsconfig.app.json
cd web && bun run build                     # regenerates the client, then tsc -b && vite build
bunx biome check .                          # lint/format for web/ and apphost.mts
```

From the repo root, `bun run ci` runs the same checks as `.github/workflows/ci.yml`.

### Regenerating the API contract

`schema/openapi.json` (consumed by Orval) and `schema/task_registry.json` are generated from the
backend and committed. After changing a route, a request/response model, or the task registry:

```bash
bun run schema             # cd server && uv run python scripts/export_schema.py
```

A test and CI fail if they are stale. Orval names each hook after the route's handler function, so
handler names must be unique across routers. Both files are written on the host, never from inside
the container (`./schema` is bind-mounted read-only there).
