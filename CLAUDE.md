# CLAUDE.md

Guidance for Claude Code sessions working in this repository. See `README.md` first for
architecture and S3 key layout — this file is about how to work in the repo, not what it does.

## Verifying changes without running the stack

This repo is orchestrated by .NET Aspire (`apphost.mts`) and needs Postgres and an S3-compatible
store running to actually execute end to end. Running the full stack (`aspire run`) is expensive
to set up and typically not available in an agent session — **don't assume you can run it, and
don't claim a change works end to end unless you've actually run it.** Default to verifying with
the checks below; if the user wants a live smoke test, they'll run `aspire run` themselves or
explicitly ask you to.

```bash
cd web    && bun run generate                  # Orval -> web/lib/api/generated (gitignored); needed before tsc on a fresh clone
cd web    && bunx tsc --noEmit -p tsconfig.app.json
cd web    && bun run build                   # tsc -b && vite build — the strongest single signal for web
cd server && uv run pytest               # pytest, server/tests/** (needs a Postgres 18 test DB; DB tests skip cleanly without one)
bunx biome check .                           # lint/format from repo root
```

**Never run two pytest sessions against the same database at once.** Each session drops and recreates
`TEST_DATABASE_URI`'s database and kills other connections to it, so a second concurrent session (or a run you
thought had died) produces `connection was closed in the middle of operation` and foreign-key failures that
look like real bugs. Give a second session its own database name in `TEST_DATABASE_URI`, and on Windows check
for a leftover `pytest.exe` before re-running (Git Bash's `ps` cannot see native processes).

## Conventions specific to this repo

- **Layering inside `server/omnitrain/`, enforced by `tests/test_layering.py`.** `core/` (constants, the plugin
  `Registry`, executors, telemetry) imports nothing else from the package; `plugins/` holds the plugin packages
  (`backends/`, `export/`, `preprocessing/`, `augmentation/`, `model_sources/`) and `api/` the HTTP layer
  (`app`, `lifespan`, `deps`, `errors`, `routers/`); `domain/` is framework-neutral logic (no DB
  session, no HTTP) and may import `core/`, `schemas`, `db.enums`, `tasks` and `backends` types; trainer backends,
  export formats and the preprocessing/augmentation ops are plugins that reach for `core/` and `domain/`, not
  `services/`; `services/` is database + S3 orchestration. A new pure helper (validation, shaping a prediction, a
  report) belongs in `domain/`, not in `services/`. Nothing outside `api/` imports it. The test holds each layer to an
  allowlist and spells out the deliberate exceptions: plugins may use `services.storage` (S3) and
  `services.plugin_settings` (the admin on/off filter), `export` still reads `db.base`/`db.models` to assemble a
  bundle, and `services` may use only `jobs.abort` and `jobs.dispatcher` (enqueue and wake; the reverse direction is
  how the work runs). Widen an allowlist only with a reason in the test.
- **No C#.** The Aspire AppHost is TypeScript (`apphost.mts`). If you're tempted to look for
  `Program.cs` or a `.csproj`, there isn't one.
- **Tasks are plugins; the task registry is the source of truth for what a task's data looks like.**
  One `Task` subclass per task in `server/omnitrain/tasks/builtin/` (any module dropped there registers at class
  creation): `id`, `label`, `modality`, `item_spec`, `annotation`, snapshot `columns`, `output`, `input_fields`,
  plus `order` for the picker. `domain/task_registry.py` is the framework-neutral lookup facade over them
  (`get_task_descriptor`, `TASK_REGISTRY`, ...): item payload shape, ground-truth/annotation type, snapshot
  columns and the inference request/response contract. Adding a task's data-side definition is one class, not
  five separate edits: no enum, migration or frontend edit, because `projects.task` is free text (a task id)
  and `POST /api/projects` validates it against the registry. `modality` and `annotation.type` stay closed
  vocabularies (ops, editors and the snapshot builder key on them), so a task that needs a new one is still a
  code change there and an `ALTER TYPE` migration. It says nothing about how a task is *trained*; that's a
  trainer backend's job (see below). The frontend task picker and per-modality UI read it via
  `schema/task_registry.json`, generated by `server/scripts/export_schema.py`; the picker's icon and blurb come
  from `web/lib/task-meta.ts`, which falls back to a generic one for a task it has not heard of.
- **Trainer backends are plugins.** One Python package per training framework in
  `server/omnitrain/plugins/backends/` (subclass `TrainerBackend`, set `id`/`label`, a `Hyperparameters`
  pydantic model, and implement `supports`/`models`/`compile`/`train`/`load`/`convert`). Ludwig is
  the shipped one (`plugins/backends/ludwig/`); it owns every Ludwig-specific concept (encoders, feature
  types, `ecd`/`llm` model types) so nothing outside that package should reference them. The
  Ultralytics YOLO backend (`plugins/backends/yolo/`: `image_classification` and `object_detection`,
  AGPL-3.0) is the second. A framework that only reads local files, as YOLO does, can't use `run.dataset_uri` /
  `run.output_uri` the way Ludwig does through s3fs: it reads the parquet, downloads each image into
  `run.workdir`, trains there, and uploads the results with `storage.upload_dir` (`yolo/data.py`,
  `yolo/train.py`). For classification its class folders are named by zero-padded class *index*,
  never by class name, so Ultralytics' `model.names` can be mapped back exactly (detection writes the
  real names into `data.yaml`, which YAML carries safely). A backend whose framework doesn't squash
  images to a square (YOLO resizes the shorter edge, then centre-crops) says so with
  `inputs[].imageResize.mode = "shorter_edge_center_crop"` in its `preprocessing_manifest`; every
  generated client implements that mode and, without the key, squashes (Ludwig's behaviour). A client
  must refuse a mode it doesn't know rather than fall back to squashing.
  `training_runs.backend` / `sweeps.backend` are free text (a plugin id), like `exports.format`,
  never a Postgres enum. A backend module's own top level must not import its heavy ML
  dependency (torch, ludwig, sklearn, ...) — listing installed backends has to work without a GPU
  runtime importable — so import it lazily inside the classmethod bodies that need it (see
  `plugins/backends/ludwig/__init__.py` for the pattern). Two contracts every backend must honor:
  `LoadedModel.output.labels` (classification class names) must come from the trained model
  artifact itself, never from the `label_classes` Postgres table (Postgres has no idea what index
  order a run assigned each class — see the export bullet below); and `train()` should report a
  `validation`-split `loss` metric wherever possible, since `events/writer.py` uses the lowest
  validation loss so far as a task-agnostic definition of a run's best epoch.
- **The scikit-learn backend (`plugins/backends/scikit/`, id `sklearn`) fits once, on a CPU.** Tabular classification and
  regression (gradient-boosted trees, random forest, a linear model) and text classification (TF-IDF with logistic
  regression or naive Bayes). There are no epochs, so the shared `epochs`/`batchSize`/`earlyStopPatience`/optimisation
  fields are refused in `compile`, while a knob that belongs to one model family (trees, regularisation) is ignored by
  the others so a sweep over the model and a knob still runs. A fit is reported as epoch 1 so the best-epoch logic works.
  A model is stored with **skops, never pickle**: a remote worker's file is loaded on the API host, and skops refuses any
  type outside `estimators.TRUSTED` (reviewed: tree node tables and `numpy.dtype`; widen it only with a reason). The class
  order is the fitted `classes_`, written to `names.json`. Its ONNX export (`skl2onnx`, `scikit/artifacts.py`) is shaped to
  what the generated clients already do for a tabular Ludwig model: one float input per column, one output named by the
  label column, **logits** for a classifier (`log(max(p, 1e-9))`, so the client's softmax gives back the probabilities).
  Imputation and scaling live in the graph, so its manifest has no `numberNormalization`. A text model takes a raw string
  and only runs in onnxruntime (it uses the `com.microsoft.Tokenizer` operator); a character-n-gram text model cannot be
  exported. skl2onnx needs `onnx.helper.make_attribute` patched for a tree ensemble with missing values (bools in an int
  list); the patch is scoped to one conversion.
  It is the **default backend for the two tabular tasks** (`default_for`, honoured by `registry.preferred_first`: the
  create-run list's first entry, and what a run uses when no backend is named). Ludwig stays offered for them, and stays
  the default for text.
- **The PyTorch backend (`plugins/backends/pytorch/`, id `pytorch`) is the code-defined alternative to Ludwig.** It trains
  image classification (torchvision classifiers with a new head; the catalog keeps Ludwig's image encoder ids:
  `resnet18`, `resnet50`, `efficientnet_b0`, `mobilenet_v3_small`, `convnext_tiny`, `vit_base`) and tabular
  classification and regression (a perceptron, `mlp_small`/`mlp_medium`/`mlp_large`) and audio classification
  (`audio_resnet18`, ImageNet weights on a one-channel spectrogram, or `audio_cnn`, from scratch), with a plain loop (`loop.py`: the
  heartbeat, schedule, clipping and mixed precision that `video` also has, plus an `Objective` for classification or
  regression and one `fit`) instead of Lightning. **What a model expects as input is one spec (`spec.py`: `ImageSpec`,
  `TabularSpec`, `AudioSpec`)**: it is stored in `names.json` with the class order, and training, evaluation, serving and the export
  manifest all read it, so none can drift from the others. `images.preprocess` does exactly what the generated clients
  do (PIL bilinear, shorter edge then centre crop; `tests/test_pytorch_backend.py` checks it bit for bit against the
  shipped Python client), which is why it uses PIL and not a torchvision transform. A table's fill value, mean and std
  are fitted on the **train split only** and applied INSIDE the module (`network.TabularNet`), so the exported ONNX takes
  raw numbers, the manifest carries no `numberNormalization`, and a client that normalised too would do it twice; a
  regressor standardises its target the same way and the graph un-does it. A knob of the other kind of input
  (`imageSize`, `dropout`, ...) is refused in `compile`, not ignored. The reported `loss` is plain cross entropy or a
  squared error in the target's own units whatever steered the optimiser (class weights, target scaling), because
  `events/writer.py` compares it across epochs. ONNX is exported straight from the `nn.Module` as logits (a number for a
  regressor), traced with two rows (a batch of 1 pins the batch axis for `convnext_tiny` and `vit_base`), and a table
  takes one tensor per column named by the column. It is **not** a default for any task (`default_for` is empty:
  scikit-learn is the tabular default, Ludwig the image one) until someone has compared it on a real run. A new input
  kind needs a new spec beside the four.
  **Bring-your-own image models** are one kind, `hf_image` (`custom.py`, `hf.py`; image classification only): a Hugging
  Face classifier or bare backbone of ViT, DeiT, BEiT, Swin, Swinv2, ConvNeXt, ConvNeXtV2, ResNet or MobileNetV2. The
  model dictates its own image size (the config's `image_size`, else the preprocessor's crop or size, else 224) and
  mean/std (`preprocessor_config.json`), read from its files when training starts (`custom.image_settings`), so
  `imageSize` is ignored (the web form always sends it) and `pretrained=False` is refused. The recipe around them is
  still `images.preprocess`, so the manifest and all six clients are unchanged. A checkpoint is loaded **strictly**
  (`hf._load_checkpoint`): `from_pretrained` re-initialises any tensor it cannot find and only warns, and for a bare
  ViT, DeiT or BEiT backbone transformers 5.14 connects none of its keys to the classifier, so the backbone is loaded on
  its own and copied in, and a tensor missing outside the head is an error, never random weights under a "pretrained"
  label. The trained model is saved as a Hugging Face folder (`config.json` and `model.safetensors` beside `names.json`,
  with `hf: true`) that points back at nothing, which is why `remote_custom_models` is True. Add a family to
  `SUPPORTED_MODEL_TYPES` and a row to `FAMILIES` in `tests/test_pytorch_custom.py` (strict load, freeze, ONNX parity).
  Validation builds the model and runs one blank image, but does not export, so a family outside that list may still
  fail at export time.
  **Bring-your-own text models** are the kind `hf_text` (text classification only; `custom.py`, `hf.py`
  `HFTextNet`; BERT, DistilBERT, RoBERTa, XLM-RoBERTa, ALBERT, ELECTRA; `tests/test_pytorch_custom_text.py`). Same strict
  loader and self-contained saved folder as `hf_image`. The model's own tokenizer is the recipe: `hf.read_tokenizer`
  takes only a **fast** tokenizer (it is data every `tokenizers` binding runs the same way) and refuses a folder with no
  tokenizer files (transformers would silently build an empty-vocabulary one); its JSON string is stored in `names.json`
  (`hfTokenizer`, with `maxTokens`, `padId`, `padToken`) and in the manifest's `inputs[0].hfTokenizer` (recipe
  `hf_tokenizer_v1`). Training and serving encode with `Tokenizer.from_str`, `enable_truncation(max_tokens)`,
  `enable_padding(length=max_tokens, pad_id, pad_token)`, exactly what the Python client does. The ONNX graph takes
  **one** int64 input `input_ids` `[batch, maxTokens]` and derives the attention mask from `ids != pad_id` inside
  (`HFTextNet`), so the pad id must be the model's `pad_token_id` (RoBERTa numbers positions from it), and `maxTokens`
  is refused above `custom.text_token_limit` (position embeddings, less `pad_token_id + 1` for RoBERTa-likes). The vocab
  settings and dropout are ignored; the learning rate defaults to `HF_TEXT_LEARNING_RATE` (2e-5), not the from-scratch
  0.002. Only the **Python** devkit implements the recipe (it needs `pip install tokenizers`); the other five clients
  gate on `textTokens`, fall through to their "adapt the client" error, and say so in the README
  (`HF_TEXT_OTHER_LIMITATION`). `BundleContext.place_model` moves the tokenizer out of `preprocessing.json` into
  `tokenizer.json` (`tokenizerFile`), because a multilingual vocabulary is megabytes. `names.json` still carries it whole.
  **Audio is one recipe in `audio.py`** (decode: scipy for WAV, torchaudio for the rest; mean to mono; `resample_poly`;
  a fixed window zero-padded at the end; Hann STFT with no edge padding; power; HTK mel filterbank; `ln(x + 1e-6)`;
  one scalar mean/std fitted on the train recordings), in numpy so it needs no torch and the same code serves training,
  evaluation and serving (`tests/test_pytorch_backend.py` checks it against `torchaudio.transforms.MelSpectrogram`).
  The recording is decoded and resampled once, in the download thread (`data.materialize(prepare=...)`), and cached as
  a `.npy`, so a file that will not decode is a skipped row. Training sees one random window per recording per epoch
  (plus SpecAugment); scoring takes `clipsPerAudio` evenly spaced windows and averages their probabilities. The ONNX
  model takes the standardised **spectrogram** (`spectrograms`, `[batch, 1, nMels, frames]`), not a waveform, so every
  generated client carries the front end: the manifest's `inputs[0].audioSpectrogram` (recipe `log_mel_v1`, which a
  client refuses if it does not know) holds every number plus the exact resampler (scipy's `resample_poly` spelled out as
  a Kaiser-windowed polyphase filter, so no client needs scipy), window rule and mel formula, and each client
  (`export/templates/*`) re-implements WAV decoding, the resampler, a radix-2 FFT and the filterbank by hand. They match
  the platform to ~5e-5 in probability (Python, TypeScript, C#, Java, the PWA in Chrome, Dart's front end; the Flutter ONNX
  session itself was never run). A client reads WAV only (8/16/24/32-bit PCM, float; the Python one also anything
  `soundfile` opens, the PWA anything the browser decodes), and a verify script skips a bundled sample it cannot read.
  `ReadmeVars.kind` is `audio` only when the manifest carries `audioSpectrogram`, so a Ludwig audio model still gets the
  old "adapt the client" README and `NotImplementedError`. Change the recipe in `audio.py` and you must change all six.
  **Text is one recipe in `text.py`**, and it is deliberately primitive so that a client in any language can repeat it
  with no Unicode tables: only the ASCII letters A-Z are lower-cased (no normalisation, no other case folding), a token is a
  maximal run of characters that are not separators (ASCII controls, space and punctuation, plus a short list of Unicode
  spaces, `text.SEPARATOR_RANGES`), and every other character, which is every non-ASCII letter, stays inside its token, so
  a Vietnamese word stays whole (a language without spaces, Chinese or Japanese, is not served). A text is the first
  `maxTokens` tokens as ids (the vocabulary position plus two; 0 is padding, 1 is an unknown word), built from a vocabulary
  fitted on the TRAIN texts only and stored in `names.json`. The models (`text_bag`, a fastText-style mean of word vectors,
  and `text_cnn`, filters over 2-4 words) train from scratch: no pretrained or transformer text model is offered. The ONNX
  graph takes int64 ids (`tokens`, `[batch, maxTokens]`), padding is masked inside it, and the manifest's
  `inputs[0].textTokens` (recipe `word_ids_v1`, which a client refuses if it does not know) carries the separator ranges and
  the whole vocabulary. Every generated client re-implements the split and the lookup (`predict` takes the text itself, never
  a path; Java and Dart call it `predictText`), and they match the platform exactly on the token ids (Python, TypeScript,
  C#, Java, Dart) and to ~5e-5 in probability (the PWA in Chrome too; the Flutter ONNX session was never run). It is `kind`
  `text` in `ReadmeVars` only when the manifest carries `textTokens`, so a scikit-learn or Ludwig text model keeps its
  old README and `NotImplementedError`. Change the recipe in `text.py` and you must change all six clients.
  The shared number report lives in `domain/regression_report.py`, beside the classification one.
- **A torch ONNX export must be a single file: pass `external_data=False`.** `torch.onnx.export(dynamo=True)` writes the
  weights to a `model.onnx.data` sidecar by default, always, even for a tiny model, and a bundle (and the S3 copy in
  `jobs/export.py`) carries only `model.onnx`, so the shipped graph cannot load. Every backend that calls it sets
  `external_data=False` and its test asserts that the output directory holds only `model.onnx`.
- **Video is a file modality with its own backend.** `video_classification` (one class per clip, like audio) is
  trained only by `plugins/backends/video/` (torchvision's Kinetics-400 classifiers, BSD-3). Decoding is OpenCV
  (`domain/video.py` to validate an upload and cut a poster frame; `plugins/backends/video/frames.py` to sample clips),
  deliberately not torchcodec, which needs FFmpeg shared libraries on the host. One sampling definition
  (`ClipSpec`: frames, stride, size, mean/std) serves training, evaluation, serving and the export manifest, and is
  written into `names.json` with the class order. Uploads of video go through the same `upload_to_pool` but are read
  one file at a time (limit `MAX_VIDEO_UPLOAD_BYTES`, 200 MB, against 50 MB for the rest; the web mirrors both in
  `lib/upload/paths.ts`). `modality` and `project_task` are Postgres enums, so a new value needs an
  `ALTER TYPE ... ADD VALUE` migration (see `0013`). Only the Python devkit decodes video (OpenCV, the
  same library the backend trains with), so `handles` (on `DevkitFormat` / `AppFormat`) leaves every other devkit and
  app with the bare ONNX model for video; they all implement object detection.
  - **Preprocessing and augmentation ops exist for video** (`plugins/preprocessing/ops/video.py`: resize, lower frame rate,
    trim; `plugins/augmentation/ops/video.py`: flip, random segment, brightness, speed, zoom). A sample is a `VideoClip`
    (all frames decoded, uint8 RGB, so `media.MAX_DECODED_VIDEO_BYTES` refuses a clip too big to hold and
    `media.worker_count` runs video one item at a time). Derived clips are always written as VP8 **WebM**
    (`media.encode_video`): MPEG-4 in MP4 does not play in browsers and H.264 needs a library the host may lack. An op
    with nothing to do must return the clip it was given (the same object), because the services read `new is sample`
    as "leave the original alone" and skip a lossy re-encode.
  - **Bring-your-own video models** are Hugging Face VideoMAE, TimeSformer and ViViT (`hf_video`, in
    `plugins/backends/video/custom.py` and `hf.py`). The model dictates its own frame count, image size and normalisation (read
    from its `config.json` and `preprocessor_config.json` when training starts, since `compile` cannot assume the files
    are on disk), and the fine-tuned network is saved as a self-contained Hugging Face folder so serving never needs
    the original files. Load the backbone strictly and replace only the head: `ignore_mismatched_sizes=True` silently
    re-initialises any mismatched backbone tensor with random weights.
- **Bounding boxes are one annotation each.** Object detection stores one `bounding_box` annotation
  per box with a `class_id`, and `label_structured = {x, y, w, h}`: top-left corner and size, as
  fractions (0..1) of the displayed image. An image with nothing in it carries one class-less
  `{"background": true}` marker, which is what tells "labelled, empty" from "never labelled": the
  snapshot's `boxes` cell is `"[]"` for the first and `null` for the second, and a trainer must leave
  the second out. All of it is validated in `domain/boxes.py` (wired in through `AnnotationIn`), so
  nothing else should re-derive the rules. Several places assume one class per item and must go
  through `task_registry.class_annotation_type(task)` instead of hard-coding `classification`: the
  item filter, class stats, merges and the health report. A class belongs to one box, so the bulk
  "classify" action refuses a detection project, and the upload route takes per-file `boxes`, never
  `classId`, for one.
- **Sweep strategies are plugins.** One `SweepStrategy` subclass per strategy in
  `server/omnitrain/sweep_strategies/` (`grid`, `random`, `random_unique`, `balanced`, `one_at_a_time`): `trials(space,
  max_trials, rng)` returns the combinations to train, all up front, and `services/sweep.expand_sweep` truncates to the
  budget. `sweeps.strategy` is free text (migration 0016), `GET /api/sweep-strategies` feeds the web's selector, and
  `queue_sweep` refuses an unknown id. A strategy cannot see earlier trials' results: a sweep is N ordinary runs
  enqueued at once, so an adaptive strategy (Bayesian, successive halving) would first need something that enqueues
  more trials as runs finish.
- **A run's headline score is not accuracy.** `services/evaluation_score.py` picks it from the evaluation report's
  `overall` block (accuracy for a classifier, mAP50 for a detector, R² for a regressor) and ships it as
  `evaluation.score` (`metric`, `label`, `value`, `higherIsBetter`) on every run summary. The runs list, the "best
  run" marker, the overview and the comparison read that via `web/lib/runScore.ts`; don't hard-code `accuracy` in a
  new place. The metrics that can be the headline are plugins (`server/omnitrain/scoring/`, one `HeadlineScore` subclass per
  metric key in `overall`, `order` = priority): a backend that reports a new kind of metric adds a class there, and
  the web needs no edit because it reads the label and direction off `evaluation.score`.
- **Some `theseus` names are deliberately kept** after the rename to OmniTrain, because they identify stored data:
  the `theseus-datasets` / `theseus-training` / `theseus-models` buckets (snapshot parquets embed `s3://theseus-datasets/...`
  URIs), the `_theseus_item_id` snapshot column, the `ctu-theseus-*` Docker volumes and Postgres database, the HKDF info
  string in `services/secrets.py`, and the local test-DB credentials. Don't "finish" the rename on them without a data
  migration.
- **Class list correctness for exports.** Any code touching model export must source the label
  index order from the trained model itself — for Ludwig, `training_set_metadata.json`'s
  `idx2str` (written into `theseus-training/{runId}/results/**/model/`), for YOLO the `names.json`
  that `yolo/train.py` writes from the trained `model.names` — never from the
  `label_classes` Postgres table. Postgres doesn't know what index a training run assigned to
  which class; getting this wrong produces a bundle that runs, returns confident predictions, and
  silently mislabels everything.
- **Export formats are plugins.** One Python class per format in
  `server/omnitrain/plugins/export/formats/` (subclass `ExportFormat`, set `id`/`label`/`group`/`artifact`,
  implement `assemble`). `GET /api/export-formats` lists them and the web's single "Export format"
  combobox renders that list, so adding a format is a new class plus a backend restart: no enum,
  migration or frontend edit. `exports.format` is free text (a plugin id), not a Postgres enum. A
  format's `artifact` names a converted-model kind (`onnx`, `torch_export`, ...); the actual
  conversion is `TrainerBackend.convert`, and a format is only offered for a run whose backend
  actually produces that artifact (`backends.registry.trainable_backends` /
  `export.registry.list_export_formats(task, backend)`).
- **Preprocessing and augmentation happen at snapshot creation, not training.** Two plugin packages,
  both driven by `build_snapshot` (`services/snapshot.py`), preprocessing first:
  - **Preprocessing** ops are deterministic and each is scoped to whichever splits (train/validation/
    test) a snapshot's config selects for it. `services/preprocessing.py` REPLACES a pool item with its
    preprocessed copy in the version's membership for exactly those splits — nothing is added, and an
    item whose ops leave it unchanged, or whose split none of them selected, stays the pool item it
    already is. A `fit`-needing op (e.g. tabular standardize) always fits on the train split's samples,
    even if train itself isn't one of its selected splits, so nothing about validation or test leaks in.
  - **Augmentation** ops are random and train-split only: `services/augmentation.py` adds N extra copies
    of each train item, made from whatever is in the train split after preprocessing ran (so a copy
    carries forward any `preprocessing` its source item had).
  - Both are Python classes, one package per concern — `server/omnitrain/plugins/preprocessing/ops/`
    (subclass `Preprocessing`, a pydantic `Params` model, `apply`) and
    `server/omnitrain/plugins/augmentation/ops/` (subclass `Augmentation`, same shape plus an `rng`) —
    served to the snapshot dialog via `GET /api/projects/{id}/preprocessing` and `/augmentations`.
  - A preprocessed or augmented item is a real `dataset_items` row with `source_item_id` set, always
    pointing at the pool ancestor directly (never at an intermediate preprocessed row — there is no
    chain of derived items). `augmentation` is set only on an augmented copy; `preprocessing` is set on
    a preprocessed item and carried forward onto an augmented copy made from one.
  - Neither is a pool item: their files live under `snapshots/{versionId}/preprocessed/` and
    `snapshots/{versionId}/augmented/`, pool dedup lookups must filter `source_item_id IS NULL`, and
    they are deleted with their snapshot (`services/derived_items.delete_derived_items`). Neither is
    replayed at inference or export time yet — a trained model only ever sees what the snapshot froze.
- **Admin switches are a filter, not a registry change.** `services/plugin_settings.is_enabled(kind, id, task)`
  is how a disabled backend, built-in model, export format, preprocessing/augmentation op or task is hidden and
  refused. Apply it in **listings** and in **validation of new work**, never in a lookup that runs work that
  already exists (`find_export_format`, `get_backend`): switching something off must only stop new use. No row
  means enabled, and a task-scoped row beats the all-tasks row. The snapshot is process-local, which is sound
  only because the service is one process.
- **Bring-your-own models have one door.** Who may see or use a custom model is decided in
  `services/model_catalog.py` (global or owner-only, `ready`, enabled, not archived, kind offered for the task),
  and ownership of the row in `services/custom_model_ops.py` (someone else's id is a 404, never a 403). Never
  trust a `custom:{uuid}` id from a request: `model_catalog.resolve` it. Where the files come from is a plugin: one
  `ModelSource` subclass per source in `server/omnitrain/plugins/model_sources/` (`hub`, `upload`; `source_kind` is free text, an
  id), which owns reference validation, first-contact pinning, fetching, whose token it uses and which of its models a
  remote worker may fetch (`worker_fetchable`, default none). A source never decides the safety rules: files are only
  ever put on disk by `services/custom_models.ensure_local` / `import_upload` (deterministic path, sha256 re-check, no pickles or
  code, no symlinks or zip-slip), and every place that trains, loads or exports a run calls
  `services/run_models.ensure_run_custom_model` first. What a model *is* (backend, kind, source, revision,
  checksum) is immutable after creation, and `training_runs.custom_model_id` is `ON DELETE RESTRICT`: a model a
  run used is archived, not deleted. A backend opts in via `custom_model_kinds`, `validate_custom_model` and the
  `custom` argument of `compile` (passed only when set, so a backend that predates it still compiles).
  A private or gated Hugging Face repo is fetched with its **owner's** saved token only
  (`services/integrations.huggingface_token_for(row.owner_user_id)`), never anyone else's and never a global
  model's. Every Hub call goes through `custom_models._hub_token`, which turns "no token" into `False`: passing
  `None` would let `huggingface_hub` fall back to `HF_TOKEN` or a cached login on the server. Tokens are only
  stored through `services/secrets.encrypt` and never returned by an API.
- **A backend's `train()` and `evaluate()` must run on a machine that has only S3 and an HTTP link to the API.**
  Training can happen on a remote worker (`omnitrain/worker/`, README "Remote training workers") that runs
  `jobs/run_core.execute`, the same function the local `train` lane runs. So `train` and `evaluate` may use S3
  (`run.dataset_uri`, `run.output_uri`, `services/storage`) and the `TrainContext` callbacks, and nothing else:
  no Postgres, no event writer, no `abort` registry, no files on the API host. `run_core` imports none of those
  either; the database half (`jobs/train.py`, `api/routers/worker.py`) wraps it. Run state still changes only through
  `EventWriter`, from the lane or from `/api/worker` handlers, never from the worker process. A run on a
  bring-your-own model is claimed by a worker only if the worker can fetch the model with no secret (an upload, or a
  public Hub model; never a private/gated one, whose owner's token stays on the server) and its backend sets
  `remote_custom_models = True` (queue `_worker_can_take_model`). Set that flag only for a backend whose TRAINED model
  loads, serves and exports from the run's results alone, because on a worker the base model's files are at a
  different path; Ludwig's are not (its checkpoint re-reads the model from the config's path), so it keeps its
  custom-model runs. Bump `PROTOCOL_VERSION`
  (`schemas/worker.py`) when the worker API's shape, a run's S3 layout or what `run_core` asks of a backend
  changes.
- **Job handlers must stay fast and idempotent.** `omnitrain/jobs/dispatcher.py` claims work off the
  domain tables themselves (`training_runs`, `model_exports` — see
  `README.md`'s "Jobs" section) with a guarded compare-and-swap
  (`UPDATE ... WHERE status = ... RETURNING`); zero rows means someone else already moved the row
  on. Follow that same pattern for any new job kind rather than doing the follow-up work inline in
  a handler that isn't guarded that way.
- **Content-addressed storage.** Dataset pool uploads are deduped per-project by sha256
  (`upload_to_pool` in `server/omnitrain/services/storage.py`). If you add a new upload path,
  reuse that helper rather than writing directly, or dedup silently breaks for that path.
- **The add-data flow is stage → review → job.** `web/lib/upload/` holds the logic and `components/dataset/` the UI.
  Staged files (`fileTree.ts`) and inline rows (`uploadQueue.ts`) both reach `ReviewTable` as `ReviewRow`s
  (`review.ts`) and the same `CommitBar`; pressing Upload runs `commit.ts` (draws every `auto` split with
  `splitPlan.ts`, a port of the server's `plan_split`; drops what the preflight marked as already present) and hands
  the units to `jobs.ts`, whose runners (`uploadStaged.ts` for files, `uploadInline.ts` for rows) send them. Anything
  that should not need a browser to test stays free of the `@public/` alias (bun test does not resolve it): the
  generated client is bound in `api.ts` / `preflightRequest.ts` and injected into the runners.
- **`web/` and the repo root are independent Bun installs**, not a workspace with `server/`.
  `server/` is a separate `uv`-managed Python project; the web app talks to it only over HTTP,
  via a generated client (`web/lib/api/generated`, from `schema/openapi.json`).
